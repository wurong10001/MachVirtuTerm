
    HP700 虚拟机 Android 移植实施方案

    一、项目概述

    本项目旨在将基于 Mach 内核的 HP700 虚拟机（项目代号：Mos / VirtuTerm）完整移植至 Android 平台。通过 Android NDK 将核心 C 语言代码编译为原生库，并结合 Java/Kotlin UI 层，实现 HP700 硬件环境在移动设备上的高保真模拟。

    项目目标：在 Android 设备上运行 HP700 ROM 镜像，支持控制台交互、图形显示、磁盘 I/O 及网络功能。

    技术栈：

    Native：C/C++ (Mach Kernel Source), CMake, Ninja, Clang

    Android：NDK 28.2.13676358, JDK 17, Gradle

    Target：arm64-v8a

    Graphics：OpenGL ES 3.2 / Vulkan

    当前状态：构建系统（CMakeLists.txt）已完成基础修复，但在编译 autoconf.c 时因缺失 types.h 头文件导致构建中断。需优先解决环境依赖与类型定义问题，随后按模块推进移植。

    二、总体架构设计

    系统采用分层架构，确保 Mach 内核代码的纯净性与 Android 平台的适配性解耦。

    1. NDK Core Library (Native C Layer)

    职责：包含所有 HP700 原始 C 源码（app/src/main/cpp/kernel/src/mach_kernel/hp_pa/HP700/）。

    特性：保持 Mach 内核逻辑不变，仅通过宏定义和适配层头文件解决 Android 环境下的类型缺失（如 types.h）及系统调用差异。

    输出：libhp700_core.so

    2. JNI Layer (Bridge Layer)

    职责：作为 Java 与 Native 的桥梁，封装复杂的 C 结构体指针，暴露最小化、线程安全的函数集。

    特性：处理 JNI 类型转换、全局引用管理、异常捕获及帧缓冲数据的零拷贝传递。

    3. Java/Android UI Layer (Presentation Layer)

    职责：提供用户交互界面，包括 GLSurfaceView（图形渲染）、KeyEvent 监听、文件选择器及设置管理。

    特性：负责将 Android 输入事件转换为 HP 扫描码，将 Native 帧缓冲纹理渲染至屏幕。

    4. VM Core (C++ Host Wrapper)

    职责：在 C++ 侧管理虚拟机生命周期，驱动模拟 CPU 循环、内存分配及 I/O 调度。

    特性：作为 JNI 的底层支撑，处理多线程同步（如 UI 线程与 VM 执行线程的分离）。

    三、分阶段实施计划

    阶段一：基础基建与类型系统修复

    目标：解决编译阻断问题，完成 Boot/Bus 配置与 Generic Bus/I/O 抽象。

    涉及模块：1 (Boot/Bus), 2 (Generic Bus/I/O)

    关键文件：autoconf.c, busconf.c, lif.h, iobus.h, bus_protos.h, types.h (新增适配)

    实施步骤：

    修复 types.h：创建 android_compat/types.h，定义 u_int8_t, u_int32_t, quad_t 等 Mach 依赖类型，映射至 <stdint.h>。

    CMake 路径注入：在 CMakeLists.txt 中 include_directories 添加适配头文件路径。

    Bus 抽象实现：在 iobus.c 中实现 readByte/writeWord，内部通过函数指针回调至 JNI 层或内存映射区。

    ROM 解析：移植 lif.h 逻辑，使用 mmap 加载 ROM 镜像，校验 LIF 卷头。

    预期产出：libhp700_core.so 可编译通过；autoconf 能成功枚举虚拟总线设备。

    验收标准：单元测试验证 readByte(0x...) 返回正确 ROM 值；无 Segfault。

    风险与应对：

    风险：Mach 旧式 K&R 声明与 Clang 严格模式冲突。

    应对：使用 -Wno-implicit-function-declaration 过渡，逐步补全原型。

    阶段二：核心设备驱动与显示

    目标：实现设备生命周期管理、VGA 图形渲染及控制台 I/O。

    涉及模块：3 (Device), 5 (Graphics), 4 (Console&I/O)

    关键文件：device.h, grf.c, grf_sti.c, cons.h, hil.c, kbdmap.h

    实施步骤：

    Device Hook：实现 device_init/destroy，建立设备链表。

    VGA 重定向：修改 grf_sti.c，将 STI 写操作重定向至共享内存帧缓冲，而非物理显存。

    JNI 纹理上传：在 JNI 层提供 updateFrameBuffer，将 Native 内存直接作为 GL 纹理源。

    键盘映射：实现 hil.c 中的扫描码生成逻辑，对接 JNI 传入的 Android keyCode。

    预期产出：屏幕显示 HP700 启动 Logo；键盘输入能在控制台回显。

    验收标准：FPS ≥ 30；按键响应延迟 < 50ms。

    风险与应对：

    风险：STI 寄存器时序敏感，渲染撕裂。

    应对：采用双缓冲机制，仅在 VSync 信号时交换指针。

    阶段三：存储与网络子系统

    目标：挂载虚拟磁盘，提供基础网络接口。

    涉及模块：7 (Disk/Storage), 8 (Networking)

    关键文件：disk.h, if_i596.c

    实施步骤：

    块设备映射：使用 MappedByteBuffer 映射 .img 文件，实现 disk_read/write。

    i596 模拟：实现 Intel 82596 命令/状态块逻辑，数据包通过 JNI 发送至 Android Tun/Tap 或 Socket。

    异步 I/O：磁盘写操作放入独立线程池，避免阻塞 VM 主循环。

    预期产出：可挂载并读写虚拟磁盘；ping 命令（若 ROM 支持）或网络初始化成功。

    验收标准：磁盘写入速度 > 10MB/s；网络包无内存泄漏。

    风险与应对：

    风险：大文件 mmap 在 32位地址空间或低内存设备失败。

    应对：实现分块读取策略，mmap 仅用于活跃区域。

    阶段四：辅助总线与平台适配

    目标：完善 EISA 枚举、串口及机器依赖入口。

    涉及模块：6 (Serial), 9 (EISA), 10 (DK helpers), 12 (Machine-dependent)

    关键文件：ite.c, eisa_common.c, gkdreg.h, machdep.mk

    实施步骤：

    串口重定向：ite.c 写操作转发至 Android UsbSerial 或 Logcat。

    EISA 翻译：在 eisa_common.c 中硬编码 HP700 常见 EISA 设备 ID。

    CPU 初始化：在 machdep.c 中设置 arm64 下的栈对齐、Cache 策略及异常向量表。

    预期产出：系统完整启动至 Shell；串口日志可见。

    验收标准：无未处理异常；EISA 设备枚举数与 ROM 预期一致。

    风险与应对：

    风险：machdep 汇编代码与 ARM64 指令集不兼容。

    应对：使用 C 语言重写关键启动路径，仅在极致性能处保留 ASM。

    阶段五：调试与性能调优

    目标：启用远程调试，优化渲染与 I/O 性能。

    涉及模块：11 (Debug/Kernel), 整体优化

    关键文件：kgdb_support.c

    实施步骤：

    KGDB Socket：实现 TCP 监听，转发 GDB 协议包至 Native 调试接口。

    Profiling：使用 Android Profiler 定位 Native 热点，优化 grf 渲染循环。

    内存池：为频繁分配的 I/O 请求实现 Slab 分配器。

    预期产出：可通过 gdb-multiarch 远程断点调试；帧率稳定。

    验收标准：调试连接稳定；内存占用 < 300MB。

    风险与应对：

    风险：调试断点导致 VM 死锁。

    应对：调试模式下暂停所有非核心 I/O 线程。

    五、关键技术方案

    1. ROM 镜像解析与内存映射

    方案：使用 FileChannel.map 创建 MappedByteBuffer，直接映射 ROM 文件至 Native 地址空间。

    优势：零拷贝，利用 OS 页面缓存，避免将整个 ROM 读入 Heap。

    实现：JNI 层获取 fd，调用 mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0)，将指针存入 vm_context->rom_base。

    2. 帧缓冲与 OpenGL ES 渲染管线

    数据流：Native grf_sti.c 写入 uint16_t* frame_buffer → JNI nativeGetFrameBuffer 返回 DirectByteBuffer → Java GLSurfaceView.Renderer 使用 GLUtils.texImage2D 或 glTexImage2D 上传纹理。

    优化：仅在 nativeMarkDirtyRect 标记区域变化时更新纹理，或使用 PBO (Pixel Buffer Object) 异步上传。

    3. 键盘事件映射

    设计：构建 static const uint8_t kAndroidToHpMap[256] 稀疏表。

    逻辑：KeyEvent.getKeyCode() → 查表 → 生成 HP HIL 扫描码序列（Make/Break） → 写入 hil_queue → VM 中断触发。

    特殊处理：组合键（Ctrl/Alt/Shift）需维护状态机，避免重复发送。

    4. 虚拟磁盘 I/O 模型

    策略：Read-Through + Write-Back。

    实现：

    Read：优先检查内存 Cache，Miss 则 pread 或 mmap 触发缺页。

    Write：写入内存 Dirty Page，后台线程定期 msync 或 pwrite 落盘。

    安全：提供 nativeFlushDisk 供 UI 层在暂停/退出时调用。

    5. 远程调试通道

    协议：TCP Socket，兼容 GDB Remote Serial Protocol (RSP)。

    实现：kgdb_support.c 中实现 put_packet/get_packet，解析 g/G/p/P 等命令，直接读写 vm_context->regs 和 vm_context->mem。

    安全：仅绑定 127.0.0.1 或提供密码验证，防止局域网劫持。

    六、构建与 CI/CD 建议

    CMakeLists.txt 模块化改造

    # 将 HP700 源码独立为 Interface Library
add_library(hp700_sources INTERFACE)
target_sources(hp700_sources INTERFACE
    ${CMAKE_CURRENT_SOURCE_DIR}/kernel/src/mach_kernel/hp_pa/HP700/autoconf.c
    # ... 其他文件
)
target_include_directories(hp700_sources INTERFACE
    ${CMAKE_CURRENT_SOURCE_DIR}/android_compat
)

# 主库链接
add_library(hp700_core SHARED jni_bridge.cpp)
target_link_libraries(hp700_core PRIVATE hp700_sources android log)

    增量编译优化

    使用 ccache：在 local.properties 或 CI 环境变量中配置 NDK_CCACHE=ccache。

    预编译头 (PCH)：将 Mach 常用头文件（types.h, param.h）打包为 PCH，减少重复解析。

    测试方案

    Native 单元测试：使用 gtest 编写 autoconf_test.cpp，在 Host (x86_64) 上验证逻辑。

    Android 集成测试：使用 Espresso + UI Automator，验证 nativeInitVM 后 UI 是否显示 Logo。

    CI 流水线：GitHub Actions，Matrix 构建 arm64-v8a，运行 ./gradlew connectedAndroidTest。
